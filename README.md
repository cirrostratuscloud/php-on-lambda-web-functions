# PHP on AWS Lambda Web Functions (proof of concept)

> ⚠️ **This is an experiment, and the whole thing was generated by an AI agent.**
> Treat it as AI slop until proven otherwise: read the code before you trust it,
> and **do not run it in production.** For real PHP on AWS use
> [Bref](https://bref.sh/), the [AWS Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter),
> or a container-image Lambda — all of which are supported and boring in the
> good way. This repo is a "huh, neat" demo, not a pattern to adopt.

## What's actually interesting here

It is *not* "you can run PHP on Lambda" — that's long solved. The point is two
things that only this setup combines:

1. **Smuggling an arbitrary runtime past a single-language contract.** Lambda
   Web Functions are **Node.js only** by design (`nodejs24.x`) — no managed PHP
   runtime, and (unlike regular Lambda) no documented custom / OS-only runtime
   path. We run PHP anyway. The Web Function contract only really demands *"be a
   process that speaks HTTP on the host:port we give you, within 10 seconds."*
   It never says that process has to be the one doing the work. So Node is a
   thin front door that spawns PHP and proxies to it. The "Node-only"
   restriction turns out to be a product decision, not a technical wall.

2. **A runtime model native Lambda PHP can't give you.** Web Functions are
   persistent HTTP servers that handle **many concurrent requests per
   environment** and bill on **active CPU**, not wall-clock-per-invocation.
   Bref and the Web Adapter on classic Lambda are one-request-per-environment
   with per-invocation billing. So this is the one way to get PHP *and* the
   concurrent-per-environment, scale-to-zero HTTP model at once — riding on a
   platform property, for free.

Whether that's worth running an undocumented hack: almost always no. But it's a
genuinely novel combination, which is the fun of it.

## How it works

```
client ──HTTPS──> Lambda endpoint ──HTTP──> index.js (Node shim) ──HTTP──> php -S (PHP app)
                                            │                               127.0.0.1:8000
                                            └ binds AWS_LAMBDA_HTTP_ENDPOINT first (beats the
                                              10s deadline), spawns PHP, proxies every request
```

`index.js` is the Web Function entry point. It binds the Lambda-provided
`host:port` immediately, spawns a bundled static PHP binary running PHP's
built-in server, waits for it to come up, then reverse-proxies every request to
it (streaming bodies through, so response streaming still works). If PHP dies,
the shim exits so Lambda recycles the environment.

The `public/` app is a small interactive dashboard that renders real
server-side PHP: version and SAPI, every loaded extension, the full native
`phpinfo()` report, and a playground that runs safe, allowlisted PHP demos
(hashing, date math, JSON validation, UUID, image generation) live.

## Prerequisites

- **AWS CLI v2** with the `lambda-web` commands (check: `aws lambda-web help`),
  with credentials and a region configured.
- **Node.js 24+** (only needed if you want to run the shim locally).
- `curl`, `zip`, and `python3` (used by the scripts).

## Use it

Everything is driven by the scripts in `scripts/` (also exposed as npm scripts).

```bash
# 1. Fetch a static Linux PHP binary into bin/php.
#    Defaults to the newest 8.3.x for linux/arm64 (matching an arm64 function).
npm run fetch-php

# 2. Deploy. Creates the Web Function, its first revision and endpoint, and on
#    first run a default IAM role + S3 bucket. Prints the endpoint URL.
NAME=php-web-poc npm run deploy

# 3. Open the printed endpoint URL in a browser to see the dashboard.

# 4. Tear it down when you're done.
NAME=php-web-poc npm run cleanup           # deletes the Web Function
NAME=php-web-poc scripts/cleanup.sh --all  # also sweeps role, S3 objects, logs
```

### Architecture must match

The function defaults to **arm64**, so the PHP binary must be `linux/aarch64`
(the default). If you deploy the function as x86_64, fetch a matching binary:

```bash
TARGET_ARCH=x86_64 npm run fetch-php
```

A mismatch is the most likely failure — the symptom is the shim staying up
while every request returns 502/503 because PHP never started. Check CloudWatch
for the `php-shim` log lines (`spawning php`, `php is ready`, `php exited`).

### Fetch options

```bash
PHP_MINOR=8.4 npm run fetch-php        # newest 8.4.x instead of 8.3.x
PHP_VERSION=8.3.15 scripts/fetch-php.sh # pin an exact patch
BUILD=bulk npm run fetch-php            # more bundled extensions (e.g. gd)
```

If the dashboard's image demo shows an SVG fallback instead of a PNG, the build
lacks `gd` — re-fetch with `BUILD=bulk` and redeploy. The live `/extensions`
page lists exactly what your binary includes.

## Cleanup notes

`aws lambda-web delete-web-function` removes the function, endpoints, and
revisions, but intentionally leaves the default IAM role, the S3 deployment
objects, and the CloudWatch log group behind. `cleanup.sh --all` (or individual
`--role` / `--s3` / `--logs`) sweeps those. It **never** deletes the managed S3
bucket itself — that bucket is shared by every `lambda-web` deployment in the
account + region. Use `--dry-run` to preview and `--yes` to skip prompts.

## Caveats (why this isn't production)

- **Undocumented behavior.** The shim relies on the Web Function environment
  allowing Node to `spawn()` an arbitrary bundled binary. AWS doesn't document
  or promise this; a runtime update could break it with no warning.
- **Double cost and a hop.** Node and PHP both live in the same 2 GB
  environment, and every request takes an extra in-process proxy hop.
- **Thin lifecycle.** No php-fpm process management, no real warmup story beyond
  the 10-second startup scramble, and "PHP died → exit and let Lambda recycle"
  is the entire recovery strategy.
- Lambda marks a revision `Active` without checking that your server listens, so
  a broken deploy can still *look* healthy until the first request.

## Files

| File | Purpose |
|------|---------|
| `index.js` | Node shim: binds the Lambda endpoint, spawns + reverse-proxies PHP |
| `public/` | Interactive PHP dashboard (`index.php`, `info.php`, `extensions.php`, API endpoints, `router.php`, assets) |
| `bin/php` | Static Linux PHP binary — fetched by `fetch-php.sh`, git-ignored (not committed) |
| `scripts/fetch-php.sh` | Download a static PHP binary into `bin/php` |
| `scripts/deploy.sh` | Deploy via `aws lambda-web deploy` |
| `scripts/cleanup.sh` | Tear down the Web Function (and optionally role / S3 / logs) |
| `scripts/build-zip.sh` | Build `function.zip` (only needed for manual API-driven deploys) |
| `.lambdaignore` | Keeps docs / scripts / git out of the deployed zip |
